## Stedi calls used at scale (all proven 9/23; key = secrets/stedi_live.key from the "stedi claude key" Gmail thread — a chat container's proxy does NOT attach the credential, the file must exist)
- `stedi.mbi(first, last, yyyymmdd, "FL", dos)` (MBILUNOSSN) ~250 calls: MBI + Part A/B plan dates + the Advantage plan as a `U` entity (type HN/PR/PS, STC 30+CQ, 'Primary Payer' name, coordinationOfBenefits date) + Part D as `R OT` STC 88 + QMB as `R QM` + `planDateInformation.dateOfDeath`. ERR 42 "Unable to Respond at Current Time" = CMS outage (retry later, 6 of 246 the first pass); ERR 72/73 = name/DOB miss (JR/SR suffixes, hyphens, two-word surnames) — 80 of 246, most of them settled by AMD's 271 on the billed plan (ACTIVE = right payer).
- `stedi.elig("CMS", first, last, dob, <chart MBI>, dos)` — the CMS route with an MBI in hand: bypasses the name match; the MSG segment carries "Railroad Retirement Medicare Beneficiary" for RRB beneficiaries (pat12182505).
- `stedi.elig("BCBSF", ..., member, dos)` / `("87726", ...)` / `("77027", ...)` on the chart member id with the DOS: FB returns planStatus + planDateInformation (periodStart/End, planBegin/End) — an FB 'active' can be a BlueMedicare product (rules.md); UHC returns the member id and plan name (an MBI passed as the member id also resolves — pat17472228 -> 9-digit UHC id); Florida Medicaid returns the coverage class ("FP | Limited to family planning services" = not a physician payer).
- `stedi.disc(first, last, dob, "FL", dos)` ($1.50, 17 calls): items[] with payer name, memberId, planDateInformation, benefitsInformation; found CMS (with MBI), UHC Dual Complete / AARP MA ids with plan windows, Simply MMA, Florida Blue BlueOptions, WellCare PDPs (= Medicare exists), family-planning Medicaid; "0 found" = uninsured (b. 1996, b. 1982 with FP-Medicaid only).

## AMD calls (no new shapes; behaviours learned)
- `ins_update.update(pid, insid, sequence="3,1")` sets the CHART default insurance order (proven again x40); an END-DATED plan cannot lead it (AMD answers insorder=""), so add the plan first, set the order, end-date last. `ins_update.update(pid, insid, enddate="mm/dd/yyyy")` end-dates in place. Concurrency fault -2147217398 "Another user has changed this insurance record" appears when another process (the sweep's getdemographic reads) touches the chart in the same second — retry.
- `add_ins.add(pid, car, member, begindate)` with begindate = Part B start (from the CMS record) — 16 plans added (8 FLO02, 3 UHCMA car302853, 2 AAR01 car6600, UNI20 car6404, BCBS car6062, SIM01 car42019).
- `freq1_visit.run(vid, cid, seq)` answers "rebill seq N -> 500" on a visit whose balance/insorder is not yet on that plan; the following `move_to_ins.move(cid, order, rebill_seq=seq)` sets the visit insorder and its rebill answers 204 — that pair is the rebill recipe (118/118 -> 204).
- `updvisitwithcharges` with insportion=0/patportion=fee on a charge that carries insurance payments UNAPPLIES them (repeat of the 9/21 lesson): the payments land in `unappliedpaymentlist` (negative amounts, `actvpaymentid`), the write-offs are voided. Repair used 9/23 on 9 charges: `move_to_ins.move(cid)` (portions back), `void_tx.void_unapplied(actvpaymentid)` per credit, `manual_post.post(cid, "FLO02", pay, contractual, "WOINS", checknumber=<original>, depositdate=<original>)` — AMD then moves the coinsurance to the patient itself (no next payer on the visit).
- getchargedetail `allowed` becomes the paid amount after a manual addpayments; a $0 addpayments (pay 0, wo 0) is accepted and harmless.
- `lookuppatient` (class lookup, name="LAST,FIR%") finds hyphenated surnames only by the first token ("POULTER,G%"), and a patient can have two charts (pat17470713 / pat17472439).
