- **Error taxonomy (write the code into the trail, never a translation):** ERR 72 means two different things on the two Medicare calls (11/10/2026). On a PLAIN check (`CMS`) it means Medicare does not know THAT NUMBER (the chart's number is wrong or old) — never "no Medicare record"; `stedi.medicare` then buys one look-up, and the look-up's answer is the result. On a LOOK-UP (`MBILUNOSSN` / `MBILU`) it means no Medicare record was found by name, birth date and state (→ commercial/Medicaid path) — still not proof: run discovery before giving up (rules.md 10/15), and on a chart whose last name carries a suffix like JR it is a name-match miss — check AMD's own 271 before flagging. ERR 73 / 75 / 76 / 58 on a plain check (name, subscriber, duplicate id, birth date not matched) take the same path; `stedi.medicare` first takes a JR / SR / II / III / IV suffix off the last name for ONE more plain check, but Medicare matches the last name WITH its suffix (rules.md 10/4): a suffix Medicare has and the chart lacks still misses — fix the chart's last name, never call the MBI wrong on an ERR 73. ERR 42 / 79 / 80 on a Medicare call = Medicare or Stedi cannot answer now: nothing else is bought, not a coverage verdict. ERR 41 on a plain check = the provider number is not cleared: `stedi.medicare` buys the look-up instead and prints "Medicare refused the plain check (41) - the look-up was bought instead" — put that line in the report. A refusal of our own provider number (41, 43, 50, 51 or 97) holds for every chart, so the rest of that run sends no plain check and goes straight to the look-up (the line says so). **ERR 62 (Centene 68069) = "Date of Service Not Within Allowable Inquiry" — the DOS is outside Centene's lookup window. It is NOT inactive:** the 9/6 sweep marked pat17469541's SUN01 plan "INACTIVE on the dates" from ERR 62 and cascaded to a facesheet request; the PCC facesheet (9/13) and AMD's 271 (ACTIVE, 9/8) showed Sunshine was and is the plan. On ERR 62: AMD's free 271 for today's status + the facility census for the DOS (see below) — never a `no` verdict. ERR 79 (CHP) = needs member id. ERR 43 (Aetna) = provider not on file but the response ECHOES the member id — a Medigap id finder. ERR 50 = provider ineligible (out of network). UHC 87726 answers 'Inactive' for Medigap members regardless of DOS — the CMS 271 is authoritative there. **A 271 that answers ACTIVE is not automatically billable: read `planCoverage`/plan details.** FL Medicaid 77027 returns statusCode 1 "Active Coverage" with `planCoverage` "FP| Limited to family planning services" — a family-planning-only Medicaid segment that does NOT cover E/M or CCM; treat it as no coverage for physician visits (Bexley 9/15, DOS 3/14–15/26). Likewise a plan whose `planStatus` is Active but whose `planDateInformation` shows the period already ended is inactive for the DOS (Centene FL Secure C20 answered Active-shell with planEnd 20260101 on a 3/14/26 lookup — note it did NOT throw ERR 62, so old-DOS Centene can return a real status too).

## The cascade (record every step as a `checks[]` entry: ok / no / na / human)
0. **Facesheet first, when there is one** (Drive folders, board drops, Pam's emails). A PCC admission record settles most of this without a lookup: "Medicaid Only-No Medicare Benefits: Yes" + "Medicare Coverage: No coverage" → **skip the MBI lookup** (no ERR 72 noise, no spend); "Primary Payer" + "Ins. Company" name the plan and the Medicaid # is the member id for SMMC plans; "Second Payer: Patient Liability" is the facility share-of-cost, not a physician payer; the Clinical Resident Profile **CENSUS block** lists the payer on every room-move line — a free, continuous payer history that answers "which plan on that DOS" (pat17469541: MCD Sunshine on every line since 11/23/2023).
1. **AMD chart** — plans + open charges (`txh.fetch`, getdemographic). Note MBI, MA numbers, SSN (last 4 only in notes).
2. **AMD's free 271** on every plan (`amd.check_eligibility(insplan_id)` / `elig_amd.py <pid> --all`, see the AMD API reference) — answers for TODAY and costs nothing; ACTIVE here settles the current plan. **Remits already in AMD** — CO24 = an Advantage plan is responsible; COB9 = hospice; PR27 = coverage terminated; CO16/N382 = bad ID; 'entity not found' = wrong payer.
3. **One Medicare answer** (11/10/2026: `python3 stedi.py medicare FIRST LAST YYYYMMDD <the chart's Medicare number, or -> <DOS YYYYMMDD> [ST]`; in a helper `stedi.medicare(first, last, dob, member_id, dos, pid=..., who=...)`; DOS = the denied date of service) — skip when step 0 says Medicaid-only. **Plain check first when the chart holds a Medicare number:** a number of the Medicare shape (11 characters once dashes and spaces are out) goes to Medicare as a PLAIN check (payer id `CMS`, the eligibility price). **The look-up when it does not, or when Medicare does not know the number:** no such number on the chart, or the plain check answers 72 / 73 / 75 / 76 / 58 (after one more plain try without the suffix when the last name carries JR / SR / II / III / IV) → ONE MBI look-up (`MBILUNOSSN` by name, birth date and state; `MBILU` only when an SSN is passed — never fetch one for this), sent with the chart's own last name, suffix and all (Medicare matches the name WITH its suffix, rules.md 10/4). 42 / 79 / 80, a time-out or an HTTP error → nothing else is bought. Either answer is the whole Medicare picture for that DOS: Part A/B dates, Medicare Advantage plan (codes U/R with entity name + coordination-of-benefits dates → bill that MA payer), Part D (R/OT = drug plan only → original Medicare), QMB/Medicaid, SNF stays (X), hospice (service type 45 on a line of its own — the Part A line itself lists 45 among the services it covers), and `planDateInformation.dateOfDeath`. **Only a look-up returns Medicare's own MBI:** in a plain answer the member number is just the number that was sent, so "the chart's MBI differs from Medicare's" can be said only from a look-up answer. In a helper, `pid=` shares the answer with the deceased-patient guard and the pre-claim check (`medicare_store.py`, one answer per chart and day under patient_db/, never the number) and feeds the date-of-death cache; the command line passes no chart id, so a date of death it shows goes on the board on William's turn by hand (as rule (e) of the nightly cascade does). Never use the MBI lookup to "correct" a commercial plan's member id (9/10: it briefly wrote MBIs onto two BCBS plans — reverted).
4. **Payer eligibility** (`stedi.elig` / `window.elig`) on every plan number you hold, with the real DOS (not the Medicare number again: step 3 already asked Medicare with it) — confirms active/inactive and plan dates, subject to the error taxonomy above (a commercial 271 listing the subscriber's own name, riders like "BLUE VIEW VISION" or "NO OTHER INSURANCE" as other/U-R entities is simply ACTIVE — only a name that maps to a real health payer is a wrong-payer signal).
5. **Insurance discovery** (`stedi.disc` / `window.disc`, $1.50) when nothing above names a payer — finds active commercial/MA/Medicaid coverage by name+DOB. 'Not enrolled with DISCOVERY' errors mean the DISCOVERY enrollment is still provisioning; retry later.
6. Only then → **human**: add a `human` trail row saying exactly what William should look up (SPOT / TMH / facility), put the row on his turn.

## Deceased-patient guard ([DOB])
DECEASED GUARD (William [DOB] - hard rule, every task): never submit, rebill or release a claim whose date of service is AFTER the patient's date of death. core/deceased_guard.py enforces it: amd.rebill_charge() refuses (409, nothing sent) and fails closed; before approving/releasing any Charge Review visit (incl. when adding modifier 25) or sending any new claim to straight Medicare (FLO02) or any CCM claim, call deceased_guard.check(pid, dos, carrier, proc) - it reads the date-of-death cache (practices/ehpa/registers/deceased_cache.json), AMD's 'deceased' field, and when needed asks Medicare through `stedi.medicare` (11/10/2026): a plain Medicare check with the number of the chart's Medicare Part B plan (car6085, an open one first, else the one that ended last), the look-up (MBILUNOSSN) when the chart has no usable number, when Medicare does not know it, or when Medicare refuses the plain check for another reason (41, 61, no Part A or Part B) - either 271 carries the date of death; a Medicare answer any helper got in the last 30 days about the same month of service or a later one (medicare_store.py) is used instead of a new call when it was asked on or after the claim's date of service (or today, for a date still to come) - an answer asked before that date cannot know of a death since, so Medicare is asked again (unless that answer already shows a date of death: a death is never undone), and a chart whose call failed today is not bought again today (it stays unverified). A care-management chart with no Medicare plan keeps the look-up by name. Blocked = do not approve/submit; VOID the charge and say it in the report - William's words of 10/4/2026 and of 11/25/2026, "void anything DOS after the date of death" and "VOID all charges sent after date of death": never re-dated, never written off, never a question for him (a care-management charge dated on or before that day is billable as it stands). A death ON RECORD whose day cannot be read here (the scrubbed copy of the cache, '[DOB]') is NOT 'no death': the guard asks again for a charge billed to straight Medicare or whose payer it is not told (11/26/2026: a charge billed to another payer is not held by it), and Medicare's answer decides - no death shown, the charge is billed and the chart named at the top of the report; only while Medicare cannot be asked is the claim not cleared - the guard raises DayLost, the check before approvals says NOT CHECKED, the feed enters no visit for the chart; merge the cache copy from Drive. A lookup that FAILS does not block, but is reported as 'date of death unverified' - unless a Medicare answer already kept in medicare_store.py shows the date of death: that death still blocks. AdvancedMD's own FREE eligibility check on the chart's Medicare plan comes first (William, 11/25/2026: amd.check_eligibility; the cache then names the source amd-medicare-271 or amd: no death on record), and the vendor is paid only when the free check gives no usable answer; DEATH_CHECK_FREE=off switches the free check off and deceased_guard.COUNTS says how many checks were asked free, answered free and bought.
- Cascade step 0 for any straight-Medicare or CCM claim: the Medicare 271 is the date-of-death source - parse DTP*442 / dateOfDeath (deceased_guard.dod_from_271) on EVERY Medicare response and record it in the cache (deceased_guard.record) - stedi.medicare / stedi.mbi / stedi.elig do this themselves when the helper passes the chart id (pid=); a plain check's 'not found' is never recorded as 'no death on record'. 9/22 audit: 181 CCM patients checked, 32 charts carried a Medicare date of death that AMD's 'deceased' field did not show.
