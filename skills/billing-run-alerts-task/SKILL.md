# Processing Run Alerts (added 9/1/2026)

## The call
`action="getclaimrunstatus" class="claimsreports" nocookie="1"` → alert-type definitions + every flagged claim run (id, date, submitter MCKGRP, totalamount, totalsent, totalexclusions, totaldroppedtopaper, exclusionreportid, alert flags). Read it EVERY run.

## Alert taxonomy → standing actions
- **1 — No clearinghouse report in 4+ days**: EDI pipeline may be down. Same-day: check with AMD support/clearinghouse.
- **2/3/6 — No insurance payment in 45+ days (run / carrier-in-run / carrier)**: identify the silent carrier; if its ERA route is known-broken (United) it's backlog — watch; if the route works, chase the payer. **Baseline 9/1/2026: 21 runs 6/12–7/17, ~$199K / 1,084 claims, all flagged — this is the recovery scoreboard; report the weekly delta as United ERA fix + VA/Tricare portals land.**
- **4 — ≥5% claims excluded**: same-day pull of that run's exclusion rows; classify: duplicates → complete (William's rule), data errors → fix+rebill, systematic payer-id/enrollment → escalate. (8/29/2026 run's 91/160 exclusions = the hospitalization start/end date error wave — since fixed and the date fix is now automated.)
- **Reading a rebill's verdict — timing rule:** a freq-1 rebill does NOT transmit on the claim run created at rebill time; it goes out on the next NIGHTLY claim run (the ~21:07 ET run), so its clearinghouse verdict is read on the FIRST 21:07 run whose `date` is after the rebill, not before. Do not declare a rebill fixed because an empty/earlier run shows no exclusion — wait for that nightly run. Proven 9/15: the 59 AET12 claims rebilled 9/14 04:20 UTC showed a clean earlier run but bounced again (PREF0288 + PREF0264) on nightly run 1700192 (9/14 21:07 ET) — verdict: not fixed.
- **5 — ≥7% dropped to paper**: payer electronic-routing/enrollment gap → feeds the credentialing project.

## Deceased-patient guard ([DOB])
DECEASED GUARD (William [DOB] - hard rule, every task): never submit, rebill or release a claim whose date of service is AFTER the patient's date of death. core/deceased_guard.py enforces it: amd.rebill_charge() refuses (409, nothing sent) and fails closed; before approving/releasing any Charge Review visit (incl. when adding modifier 25) or sending any new claim to straight Medicare (FLO02) or any CCM claim, call deceased_guard.check(pid, dos, carrier, proc) - it reads the date-of-death cache (practices/ehpa/registers/deceased_cache.json), AMD's 'deceased' field, and when needed runs a Stedi Medicare lookup (MBILUNOSSN) whose 271 carries the date of death. Blocked = do not approve/submit; VOID the charge and say it in the report - William's words of 10/4/2026 and of 11/25/2026, "void anything DOS after the date of death" and "VOID all charges sent after date of death": never re-dated, never written off, never a question for him (a care-management charge dated on or before that day is billable as it stands). A death ON RECORD whose day cannot be read here (the scrubbed copy of the cache, '[DOB]') is NOT 'no death': the guard asks again for a charge billed to straight Medicare or whose payer it is not told (11/26/2026: a charge billed to another payer is not held by it), and Medicare's answer decides - no death shown, the charge is billed and the chart named at the top of the report; only while Medicare cannot be asked is the claim not cleared - the guard raises DayLost, the check before approvals says NOT CHECKED, the feed enters no visit for the chart; merge the cache copy from Drive. A lookup that FAILS does not block, but is reported as 'date of death unverified'. AdvancedMD's own FREE eligibility check on the chart's Medicare plan comes first (William, 11/25/2026: amd.check_eligibility; the cache then names the source amd-medicare-271 or amd: no death on record), and the vendor is paid only when the free check gives no usable answer; DEATH_CHECK_FREE=off switches the free check off and deceased_guard.COUNTS says how many checks were asked free, answered free and bought.
