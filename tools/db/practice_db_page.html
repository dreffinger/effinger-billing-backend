Is it working?

Permanent store and web app

Where the database lives

In two places. The working copy is inside this page: every claude.ai artifact can carry its own document database, and this one does. The documents are JSON, grouped in collections, stored by claude.ai with the artifact and kept across republishes. They are readable by whoever can open this page and writable only by the owner and by Claude sessions acting as the owner. The page reads this copy and nothing else.

The permanent store is Neon Postgres (since 11/6/2026): organization ehpa, project ehpa-database on AWS us-east-1, HIPAA enabled, Business Associate Agreement with Databricks accepted. Every document a run writes here is copied there by the same run (what a chat session writes here follows with the next full copy of this database), next to every other billing page’s database, the registers and reports on GitHub main, and a log of every routine run. It is the one place the practice’s patient data is meant to rest, and the one place a question can cross two boards in SQL. The section below says what was set up and what is in it.

Nothing here lives on GitHub or Drive at read time. GitHub main stays the record the routines write first; after each run a helper turns those files into documents, the run stores them here with one call per batch file and copies the same documents to Neon with one command. Drive keeps what must never be in a shared page (patient names, facesheets, HL7 files); this database holds chart ids, dates, codes and dollars only.

How it was built, in what languages

  • Python 3 helpers do the work: claimocity_ingest.py parses the HL7 v2.4 DFT^P03 feed, matches charts and enters charges through the AdvancedMD XML API; claimocity_verify.py runs eligibility (AMD 271, Stedi X12 270/271); claimocity_recon.py pairs every feed message with its AdvancedMD outcome; practice_db.py turns registers and reports into documents.
  • Bash + runbooks (Markdown) tell each scheduled run what to do; the routine prompts point at the runbooks on main.
  • JSON registers on GitHub main are the record; git mirrors them to the synced branch, Postman and Drive.
  • HTML, CSS and plain JavaScript make this page; it computes every figure from the documents in the browser (no server, no library).
  • Postgres on Neon is the permanent store: tools/db/neon_db.py (Python; psycopg or pg8000 over the wire protocol, else Neon’s HTTPS SQL endpoint) writes every document and every run there, and tools/db/neon_schema.sql builds the typed ehpa.* views a report queries in SQL.
  • Google Cloud: a Cloud Run job copies the Claimocity SFTP files into a private bucket every 30 minutes; the routines read the bucket with a read-only key.

Capabilities the database gives the practice: a complete, searchable record of what the feed sent and what was billed; a daily health check without opening AdvancedMD; a place every routine can write to and every page can read from; raw JSON for any analysis; and the ability to add collections (credentialing, deposits, denials) without new plumbing.

One door
tools/db/neon_db.py: init (schemas, tables, views), load-writes (the documents a run just built), load-docs and load-page (another board’s database and page), load-files (registers and reports on main), run-log (one row per routine run), egress-test (which network paths reach the database), set (the HIPAA marker row), health, and a read-only sql. Every load refuses to run until the HIPAA marker row exists, unless a person passes --no-phi-check on purpose, so nothing with a chart id lands in an unflagged project by accident.
Three layers
raw.* keeps every document exactly as its source wrote it (one row per collection and document id, JSON body, SHA-256, upserted, never duplicated); ops.* keeps what each routine run did and what each load did; ehpa.* are 27 views built from raw.* by tools/db/neon_schema.sql: one row per billing run, run step, ERA line, CARC code, feed charge, cascade night, approval package and routine run. Views, not copies, so nothing drifts from the source.
Loaded so far

From this database: billing runs 427, ERA runs 211, snapshots 35, copies of other pages 29, feed checks 24, feed batches 10, page index 9, cascade nights 7, master data 3. From the other boards: Insurance Refresh Board 474 items and 6 drops, Mandatory approvals 97, Credentialing 42, ehpa home 20 questions, and the embedded datasets of the Button, Money Ledger, Outstanding Claims, Treasury Payments, Programming Lab, Working Denials, ehpa Finance and AR aging pages, and the Goals of Care note. From the repository: 1,788 register files, 438 engine reports, the cascade nights and the feed report.
Who writes, when
every billing run (the Button, the 6-hourly columns run, the nightly cascade, the daily feed) runs load-writes right after its ArtifactData batches and run-log with its one-line headline; the daily practice-database sync, once William creates it, adds every board’s database and page. If the cloud environment’s network policy blocks the Neon hosts (the bootstrap’s network probe prints NEON_BLOCKED), the run reports “no path to the database” and goes on; the artifact batch stands on its own, and the documents reach Neon with the next full copy of this database (loads are upserts by hash, so nothing is duplicated).
Secrets
for the routines, the connection string is the NEON_DATABASE_URL credential of the routine environment or, when absent, a git-ignored secrets file written once per container from a Gmail thread, the way the Stedi and GitHub keys are; it is never printed, committed, put on Drive or in a digest. The routines connect as the role ehpa_routine, which can insert and update but not delete. This page shows nothing from it and does not read Neon (a browser has no credentials); the figures above come from the writer’s own health line.

The triple mirror

The record is GitHub main (dreffinger/effinger-billing-backend): code, runbooks, PHI-light registers and reports. Every change is also pushed to the synced branch the claude.ai Project reads, mirrored to the Postman workspace (API vocabulary and collections) and copied to Google Drive (runbooks, prompts, digests, the PHI state bundle). This database is the fourth copy of the structured data, and the one the pages read; since 11/6/2026 Neon Postgres holds a fifth, permanent copy of the structured data (see The permanent store on Neon).
